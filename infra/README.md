# Infrastructure runbook

Everything the closed beta runs on in Azure is defined in Terraform under `infra/azure`.
Nothing here has been applied yet. Follow this runbook once per subscription, then let
GitHub Actions deploy.

## What gets created

One resource group per environment (`rg-dtr-dev`, `rg-dtr-staging`, later `rg-dtr-production`)
contains:

| Module                         | Resources                                                                                 | Notes                                                                                                                                               |
| ------------------------------ | ----------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `modules/container-apps`       | Container Apps environment + one Container App (1 vCPU, 2 GiB, exactly 1 replica)         | HTTPS ingress with WebSockets, `/healthz` liveness, `/health/ready` readiness. Rooms live in memory, so `max_replicas` is fixed at 1.               |
| `modules/container-registry`   | ACR Basic                                                                                 | Admin user off. The app pulls with its managed identity (AcrPull); GitHub pushes with OIDC.                                                         |
| `modules/key-vault`            | Key Vault (RBAC) + `room-token-signing-key` and `telemetry-hash-salt` secrets             | Values generated by Terraform (`random_password`), never in code. Only the app identity can read them. Purge protection on for production.          |
| `modules/blob-storage`         | Storage account (Entra ID only, no shared keys), `telemetry` and `audit` containers       | Lifecycle rules: telemetry 90 d, audit 365 d, privacy requests 730 d, beta reports 365 d. The audit container has a write-once immutability policy. |
| `modules/application-insights` | Log Analytics, Application Insights, beta operations workbook, 4 log alerts, action group | KQL in `queries/*.kql` reads the `msg: "telemetry"` log lines the server writes (see "Telemetry" below).                                            |
| `modules/cdn`, `modules/waf`   | Front Door Standard + WAF policy                                                          | **Off** (`enable_front_door = false`). Container Apps already terminates TLS. Turn on later without code changes.                                   |
| `modules/github-oidc`          | Entra app + federated credentials per GitHub Environment + scoped role assignments        | Used by `bootstrap/` only. No client secrets exist anywhere.                                                                                        |

`bootstrap/` creates the resource groups, the Terraform state storage account (Entra ID only,
versioned) and the GitHub OIDC identity.

The backlog mentions `.bicep` files (blob lifecycle, Key Vault, OIDC, dashboards). They are
implemented as the Terraform modules above so there is a single IaC tool.

## Prerequisites

- Azure CLI (`az`) and Terraform 1.9 or newer.
- On the target subscription: **Owner** (to create role assignments), and in Entra ID
  **Application Administrator** (to create the GitHub OIDC app). Only the bootstrap needs this.
- Region: examples use `westeurope`.

## 1. Bootstrap (once per subscription)

```sh
az login
az account set --subscription "<subscription name or id>"

cd infra/azure/bootstrap
terraform init
terraform apply \
  -var 'github_repository=jesper-bjerre/Donkey-Trump-Race' \
  -var 'environments=["dev","staging"]'
terraform output
```

Keep the bootstrap state file safe (it has no secrets, but you need it to change the bootstrap
later, for example to add production). The outputs give you:

- `state_backend`: values for `infra/azure/env/<env>.backend.hcl`.
- `github_actions`: the repository variables for step 3.

## 2. First apply of an environment (optional, from your machine)

GitHub Actions can create everything on the first push to `main`. To apply by hand instead:

```sh
cd infra/azure
cp env/dev.tfvars.example env/dev.tfvars              # fill in; git-ignored
cp env/dev.backend.hcl.example env/dev.backend.hcl    # values from the bootstrap output
terraform init -backend-config=env/dev.backend.hcl
terraform plan  -var-file=env/dev.tfvars
terraform apply -var-file=env/dev.tfvars
terraform output app_url
```

With `container_image` empty, the app runs a public placeholder image until the first deploy
pushes the real one.

## 3. GitHub configuration

This step can be done later, on another machine.

Repository variables (Settings → Secrets and variables → Actions → Variables). None of them
are secret:

```sh
gh variable set AZURE_CLIENT_ID          --body "<github_actions.AZURE_CLIENT_ID>"
gh variable set AZURE_TENANT_ID          --body "<github_actions.AZURE_TENANT_ID>"
gh variable set AZURE_SUBSCRIPTION_ID    --body "<github_actions.AZURE_SUBSCRIPTION_ID>"
gh variable set TFSTATE_RESOURCE_GROUP   --body "<github_actions.TFSTATE_RESOURCE_GROUP>"
gh variable set TFSTATE_STORAGE_ACCOUNT  --body "<github_actions.TFSTATE_STORAGE_ACCOUNT>"
```

Environments `dev` and `staging` (Settings → Environments), each with these variables:

```sh
for env in dev staging; do
  gh api -X PUT "repos/jesper-bjerre/Donkey-Trump-Race/environments/$env"
  gh variable set AZURE_RESOURCE_GROUP --env "$env" --body "rg-dtr-$env"
  gh variable set AZURE_LOCATION       --env "$env" --body "westeurope"
  gh variable set ALERT_EMAIL          --env "$env" --body "<ops e-mail or empty>"
done
# After the first staging deploy, for the on-demand smoke workflow:
gh variable set STAGING_BASE_URL --env staging --body "https://<staging app url>"
```

Restrict the environments to the `main` branch (deployment branch policy). The OIDC
federated credentials only trust these environment names.

## 4. Deploying

- **dev**: every push to `main` runs `.github/workflows/deploy.yml`. It validates, builds the
  image, runs a Trivy scan, runs `terraform plan/apply` with the image tagged by the git SHA,
  then smoke-tests `/healthz` and runs `pnpm smoke:staging` against the new URL.
- **staging**: Actions → Deploy → Run workflow → `staging`.
- **production**: see the next section.

To roll back, re-run the Deploy workflow for an older commit. Every image is tagged with its
SHA and the Terraform state is versioned.

## 5. Adding production later

1. Run the bootstrap again with `-var 'environments=["dev","staging","production"]'`.
2. Create the `production` GitHub Environment with **required reviewers** and the variables
   from step 3 (`AZURE_RESOURCE_GROUP=rg-dtr-production`).
3. Actions → Deploy → Run workflow → `production`. The job waits for approval before it gets
   Azure credentials.

Production turns on Key Vault purge protection and locks the audit immutability policy.
**Locking cannot be undone.**

## Secrets and rotation

- `room-token-signing-key`: rotate with
  `terraform apply -replace=module.key_vault.random_password.room_token_signing_key`.
  Then restart the revision (`az containerapp revision restart ...`). Existing room tokens
  become invalid, so players rejoin. Do this between beta sessions.
- `telemetry-hash-salt`: rotating it splits pseudonyms, so hashes before and after no longer
  match. Only rotate it at the end of a beta phase.
- The generated values are also in Terraform state. That is why the state account is private,
  Entra ID only and versioned.

## Telemetry, dashboards and alerts

The server writes telemetry two ways:

- **Blob storage**: JSONL batches at `telemetry/year=/month=/day=/roomHash=/matchEvents.jsonl`.
  This is the long-term evidence.
- **Structured log line**: `msg: "telemetry"` in the container logs, which Log Analytics
  collects.

The **beta operations workbook** and these alerts run on the log lines:

- match-breaking errors > 0 in 15 min (severity 1)
- disconnect spike > 50 in 5 min
- join failures > 10 % in 1 h
- major desync in > 5 % of matches in 1 h

Set `alert_email` to get e-mails.

To build the beta sign-off report from the stored telemetry:

```sh
pnpm beta:summary -- --releaseCandidateId rc-2026-12-15 \
  --source azure:https://<storage account>.blob.core.windows.net
```

This needs Storage Blob Data Reader or Contributor on the account. Review
`docs/beta/release-gates.json` (legal/IP, privacy, accessibility) before running it.

## GDPR requests

`POST /api/v1/privacy/requests` (the form on `/privacy`) stores
`privacy/requests/<id>.json` in the `telemetry` container. It holds the request type, the
contact e-mail and a salted hash of the subject's own description. The request is also
audit-logged.

Telemetry never contains nicknames, room codes, tokens or IP addresses, so most requests are
answered by confirming that no personal data is held beyond the request itself. Delete
request records once they are resolved. The lifecycle rule removes them after 730 days
regardless.

## Validation without Azure

```sh
terraform fmt -check -recursive infra/azure
terraform -chdir=infra/azure init -backend=false && terraform -chdir=infra/azure validate
terraform -chdir=infra/azure test          # mocked providers; no credentials needed
terraform -chdir=infra/azure/bootstrap init -backend=false && terraform -chdir=infra/azure/bootstrap validate
```

CI runs the same checks in the `Terraform` job of `validate.yml`.
